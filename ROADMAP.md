# Roadmap

Directional priorities—not guarantees. Community feedback and maintenance capacity can change this plan.

## Phase 0 — Public foundation (current)
- [x] Publish mission and invitation.
- [x] Document account/project boundaries.
- [x] Establish contribution, security, governance, and discovery guidance.
- [ ] Enable GitHub Discussions and choose categories.
- [ ] Invite feedback and identify early collaborators.
- [ ] Review links, onboarding, and accessibility.

## Phase 1 — Discovery and project map
- [ ] Maintain an index of relevant projects and standards.
- [ ] Define lightweight project metadata.
- [ ] Add AI-friendly navigation and machine-readable descriptions.
- [ ] Keep status, license, maintainer, and activity visible.
- [ ] Link existing registries rather than copying them.

## Phase 2 — Interoperability and coordination
- [ ] Survey standards before proposing new ones.
- [ ] Publish integration recipes and compatibility tests.
- [ ] Explore human/agent handoff and approval patterns.
- [ ] Document provider/model portability.

## Phase 3 — Reliability and evidence
- [ ] Define claim/evidence statuses and source provenance.
- [ ] Prototype evidence-aware output contracts.
- [ ] Evaluate unsupported claims, injection, context loss, and tool failures.
- [ ] Include abstention and uncertainty in evaluation.
- [ ] Publish limitations and methodology.

## Phase 4 — Decentralization and resource control
- [ ] Document local-first and federated patterns with tradeoffs.
- [ ] Prototype provider-independent budgets, quotas, and stop conditions.
- [ ] Test portability and fallback.
- [ ] Evaluate privacy and operational complexity.

## Phase 5 — Community projects and releases
- [ ] Select projects based on demonstrated need and maintainer capacity.
- [ ] Require a working proof or testable specification before calling work usable.
- [ ] Publish releases with changelogs, tests, and migration guidance.
- [ ] Establish maintenance and sunset reviews.

## Maturity labels
| Status | Meaning |
|---|---|
| idea | Opportunity identified; not validated. |
| spec | Behavior documented; implementation may not exist. |
| prototype | Experimental; gaps and breaking changes expected. |
| usable | Tested for a defined use case; limitations documented. |
| stable | Maintained release with compatibility expectations. |
| maintenance | Critical/security fixes; limited features. |
| archived | No active development; alternatives documented. |

Review roadmap and project health at least quarterly. Each project should identify a maintainer, issue path, test strategy, and maintenance plan before being called production-ready.
